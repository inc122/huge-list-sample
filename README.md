# Список из 1 000 000 элементов

Тестовое задание на позицию Fullstack-разработчика. Приложение со списком из
1 000 000 элементов (ID 1..1 000 000): выбор элементов, фильтрация,
изменение порядка выбранных элементов через Drag & Drop.

## Стек

- **Backend:** Express.js + TypeScript, данные — только в оперативной памяти (без БД).
- **Frontend:** React + Vite + TypeScript, `@dnd-kit` для Drag & Drop.

## Запуск

Требуется Node.js 18+.

```bash
npm install
npm run dev
```

Это поднимет:

- backend на `http://localhost:3001`
- frontend (Vite) на `http://localhost:5173`, проксирующий `/api/*` на backend.

Откройте `http://localhost:5173`.

### Сборка

```bash
npm run build
npm start
```

`npm start` поднимает только собранный backend (`server/dist`). Собранный
frontend (`client/dist`) — статика, которую нужно раздать любым сервером
статики или веб-сервером (nginx и т.п.) при деплое.

## Структура

```
server/   Express API, состояние в памяти, очередь батчинга запросов
client/   React SPA
```

## Архитектурные решения

### Хранение 1 000 000 элементов

Базовые элементы (ID 1..1 000 000) материализуются в памяти сервера как
настоящий массив объектов `Item[]` при старте (`server/src/store.ts`,
`baseItems`) — не вычисляются на лету при каждом запросе. Дополнительно
хранятся:

- отсортированный массив ID, добавленных пользователем вручную (обычно за
  пределами базового диапазона);
- множество и порядок выбранных ID (`selectedSet` / `selectedOrder`).

Такой массив занимает заметную, но некритичную часть памяти процесса
(десятки–сотни МБ, в зависимости от рантайма) — это сознательный выбор в
пользу буквального соответствия формулировке задания («список из
1 000 000 элементов»), а не оптимизация. Ленивое вычисление (`label = Item
${id}` по формуле, без хранения) было бы эквивалентно по поведению API и
существенно дешевле по памяти — этот вариант тоже рассматривался и
реализовывался, но был заменён на материализацию по прямой просьбе.

### Очередь запросов, дедупликация, батчинг (раздел 6 задания)

`server/src/batchQueue.ts` — универсальная очередь `BatchQueue(intervalMs)`:

- все вызовы `enqueue(key, fn)` с одинаковым `key`, поступившие в одном
  временном окне, схлопываются в один вызов `fn`, а результат отдаётся всем
  вызывавшим — это и есть дедупликация запросов и техническая гарантия того,
  что операция (например, добавление одного и того же ID) не будет выполнена
  дважды;
- все операции, накопленные за `intervalMs`, обрабатываются последовательно
  на одном тике (единая очередь обработки).

Используются два инстанса:

- `addQueue` (10 секунд) — только для `POST /api/items` (добавление нового
  элемента);
- `rwQueue` (1 секунда) — для чтения списков и модифицирующих операций
  (выбор/снятие выбора/изменение порядка).

HTTP-запрос от клиента "висит" до тех пор, пока не пройдёт очередной тик
очереди — то есть сама задержка ответа и есть батчинг, никакого отдельного
поллинга на клиенте не требуется.

### Drag & Drop при активном фильтре

Клиент не пересчитывает абсолютные индексы. Вместо этого при завершении
перетаскивания вычисляется "переместить элемент X перед элементом Y" (Y —
конкретный сосед, видимый в текущем, возможно отфильтрованном, списке).
Сервер применяет эту операцию к полному порядку (`selectedOrder`), поэтому
элементы, скрытые фильтром, не теряют своей относительной позиции.

### Фильтрация и пагинация

Фильтр — подстрока в десятичной записи ID (`String(id).includes(search)`).
Оба списка (слева и справа) пагинируются по `offset` (позиция в
отфильтрованной последовательности), а не по курсору: клиент передаёт
`offset` и `limit`, сервер сканирует ID по возрастанию, пропускает первые
`offset` совпадений и возвращает следующие `limit`. Это единообразно для
обоих контейнеров, но у него есть цена: для левого списка (потенциально до
1 000 000 элементов) стоимость одного запроса растёт линейно с `offset` —
каждая следующая порция требует повторного сканирования всех уже
просмотренных ID с начала. Так как чтения батчатся (не чаще раза в секунду)
и в рамках теста глубина прокрутки ограничена, это приемлемо; для реальной
нагрузки с глубокой прокруткой миллиона строк тут напрашивается курсор
(последний увиденный ID) вместо offset — но по вашей просьбе оставлено
единообразие через offset.

### Персистентность

Выбранные элементы и их порядок хранятся на сервере (в общей для всех
пользователей памяти) и просто запрашиваются заново при перезагрузке
страницы — никакого `localStorage` не требуется. Значения фильтров хранятся
только в состоянии React-компонентов и, соответственно, теряются при
перезагрузке — как и требуется по заданию.

## Известные ограничения (сознательно не реализовано, вне объёма задания)

- Правый список не виртуализируется (не используется windowing), чтобы не
  усложнять совместимость с Drag & Drop — при выборе очень большого числа
  элементов (сотни тысяч) рендер списка в DOM станет узким местом. Для целей
  теста и типичного объёма выбора (десятки/сотни элементов) это не является
  проблемой.
- Полный rollback оптимистичного обновления реализован для выбора/снятия
  выбора, но не для reorder (при сетевой ошибке порядок на клиенте может
  разойтись с сервером до следующей перезагрузки страницы).
- Деплой на хостинг не выполнялся — задание тестировалось локально.
